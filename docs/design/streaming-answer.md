# 评审稿：回答流式呈现（B1 真流式）立项

> 状态：**待拍板**。作者：执行会话。日期：2026-08-27。
> 背景：封版后优化审计（A/B/C/D 分级）中 B 级最大项。按惯例先评审后实施。

## 1. 问题

`answer.delta` 事件当前是**完成态伪流式**：综合器的完整 JSON 返回、finalize 结束后才一次性发送全文（application.py `emit({"type": "answer.delta", ...})`）。用户从提交到看到任何正文的等待 = 整个回合的 LLM 链时长（实测单轮 10-30s，多跳 40s+），期间仅有三个 stage.changed 文案。

## 2. 目标与非目标

**目标**：首屏反馈时间从"回合结束"提前到"综合开始后数秒"。
**非目标**：不做逐 token 的裸流（JSON 合同下不可靠）；不改 API/WS 事件 schema 的既有字段语义。

## 3. 方案

### 方案 D（推荐先做）：进度增强——零合同风险

不改模型调用方式，把**已有事件类型**用起来：

1. plan 节点完成后立即推送"研究计划预览"事件（`stage.changed` 的 data 扩展子问题列表，或复用 evidence.ready 的 data 形态新增 plan.ready 事件——后者需前端配合，仍向后兼容：旧前端忽略未知 type 即可，但按红线"WS 合同向后兼容"，**新增事件类型是允许的演进**（与 turn.cancelled 先例一致）。
2. retrieve 节点每完成一个查询批次就推送 `evidence.ready`（当前只在最终 finalize 后发一次）。前端"已找到 N 条证据"实时递增。

- 效果：用户 2-3 秒内看到"正在分析 → 子问题清单 → 已找到 5 条证据"，等待感大幅下降。
- 工作量：半天（application 事件点 + 前端两处渲染 + 测试）。
- 风险：接近零；事件频率需节流（每节点一次，非每条）。

### 方案 A（二期可选）：两段式真流式

1. 综合器第一次调用：只生成正文段落纯文本（流式 API 透传 → answer.delta 逐段推送）。
2. 第二次轻量调用（可走 MODEL_NAME_LIGHT）：从正文抽取 claims + limitations，完成态发带引用编号的最终 answer.delta 覆盖。

- 效果：首字可见 <5s。
- 代价：每回合 +1 次 LLM 调用；正文首版无 [n] 引用编号（完成态替换）；claims 与正文可能脱节需一致性校验（复用 finalize 的证据 ID 交运算即可）。
- 工作量：2-3 天含测试；WS 前端需支持"delta 覆盖"语义。
- 风险：中。两次调用间模型行为不一致时正文与 claims 错位——finalize 交运算兜底后最坏是引用缺失而非错误引用。

### 已否决

- **结构化流式 JSONL**：DeepSeek json_object 模式无法保证中途可解析，兼容性不可控。
- **裸 token 流**：JSON 合同下前端无法增量渲染，只增加噪声。

## 4. 建议

**先做 D**（半天、零风险、立即改善等待感），**A 挂二期**视 D 上线后的实际体验反馈决定是否立项。

## 5. 验收口径

- D：提交后 ≤3s 收到含子问题的事件；每轮检索完成即收到 evidence 计数更新；既有 687 测试全绿 + 新增事件序列契约测试。
- A（若立项）：首字可见 ≤5s；完成态正文与 claims 引用一致性由既有 finalize 合同保证；flag 或事件版本开关可回退。
