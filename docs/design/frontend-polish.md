# 设计评审稿：前端交互与视觉优化（参考 zcode 客户端交互范式）

> 状态：**方案阶段，暂不实施**（用户 2026-08-31 委托拟定）。
> 参考：ZCode 客户端的交互范式（设计原则借鉴，非像素照抄——Web 前端与
> 终端客户端形态不同，取其信息组织与交互逻辑）。

## 1. 现状问题（基于 J1 展示审阅轮 + 用户 Dify 五轮实测）

1. **等待体验断层**：流式已有（partial 气泡），但"规划/检索"阶段用户只看
   到一行 stage 文案滚动，过程信息（子问题、每轮证据计数）存在但展示弱；
2. **信息密度不均**：证据卡占用大量纵向空间（每卡含引文全文），一轮 6-8
   条证据需要数屏滚动；limitations 展开面板层级深；
3. **视觉语言不统一**：浅色底+绿色点缀，与"研究工具"的严肃定位和终端
   系工具（zcode/codex/pi 均深色）的审美惯例不一致；
4. **交互通道单一**：纯鼠标流；Esc 中断回合（后端 turn.cancelled 已支持）
   无前端入口；无会话快速切换快捷键；
5. **回答排版**：引用编号 `[1][2]` 与正文混排样式单薄；limitations 的
   内部诊断已过滤（J1）但"模型自拟的限制说明"与系统声明无视觉区分。

## 2. 从 zcode 客户端借鉴的交互原则

1. **渐进披露**：默认只展示结论与状态，过程（计划/检索/工具调用）折叠
   为可展开的时间线——"想看的人随时能看，不想看的人不被打扰"；
2. **状态行模式**：固定一行紧凑状态（当前阶段+计数），完成后收敛进历史，
   不留大块中间状态；
3. **流式优先**：一切长任务都有增量反馈，没有任何"完成后一次性出现"的
   大块内容；
4. **中断随时可达**：运行中任务始终一键可取消（Esc）；
5. **深色终端美学**：低对比背景+高对比前景+等宽字体呈现代码/数据，
   主题统一贯穿所有面板。

## 3. 分项方案（建议三期）

### 第一期：信息架构与渐进披露（工作量中）

- **回合时间线**：每回合内把 plan.subquestions / 每轮证据计数 / 补充轮
  渲染为可折叠时间线（数据已有：plan.ready 与 evidence.progress 事件），
  默认折叠为一行摘要"已规划 3 个子问题 · 3 轮检索 · 15 条证据"；
- **证据卡紧凑化**：默认只显示 标题+来源徽标+分数，引文折叠；支持
  "展开全部"快捷键；同源证据合并计数；
- **limitations 分级渲染**：系统声明（降级/预算耗尽）与模型自拟说明
  分区展示——后端已在 limitations 中以文案区分，前端按前缀分类。

### 第二期：主题与视觉（工作量中）

- **深色主题默认**：#0d1117 底 / #e6edf3 字 / 绿色 accent 收敛为单一
  品牌色（当前 #1a73e8 蓝与绿色系混用问题一并解决）；CSS 变量化，
  保留浅色可选；
- **等宽字体用于**：引用编号、证据 locator、代码片段、chunk 定位串；
- **排版规范**：回答区行高 1.8、段落间距固定、引用编号上标化悬浮预览
  （hover 显示对应证据卡摘要）。

### 第三期：交互通道（工作量小-中）

- **Esc 中断回合**：连接既有 `DELETE /turns/{id}`（turn.cancelled 事件
  后端已支持）——运行中发送按钮变为"停止"；
- **Cmd/Ctrl+K 会话快速切换**（模糊搜索）；
- **队列消息**：运行中输入 follow-up 回车排队（对齐 pi 的 steering
  语义，后端 WS 通道已可承载）。

## 4. 明确不做

- 不做像素级复刻 zcode（终端组件与 Web 组件形态不同）；
- 不做多窗口/分屏（超出产品定位）；
- 不引入重 UI 框架（保持现有 React+CSS 变量方案）。

## 5. 验收口径

- 每期落地后：vite build + vitest 全绿；用户实测一轮 Dify 五轮剧本，
  确认等待感知与信息获取效率提升；不引入新的 WS/HTTP 合同变更
 （第一/三期仅消费既有事件与端点）。

## 6. 建议

第一期限量先行（渐进披露+证据卡紧凑化对信息密度改善最直接），
第二期主题改造独立分支（视觉回归面大），第三期随第一期顺带。
