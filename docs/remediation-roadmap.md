# 工程整改路线图

> 文档用途：记录当前工程中值得在简历展示、公开演示或进一步部署前修复的问题。
>
> 当前结论：工程已经足够作为简历个人项目，核心完成度较高；但更准确的定位是“面向个人部署的多轮研究助手原型”，暂不宜表述为生产级、高并发、多实例平台。
>
> 本文只描述待修复事项，不代表已经实施。实施时应遵守项目中的“一项任务一个 commit”、红线约束和 RED-first 测试纪律。

## 1. 当前工程评价

项目已经具备比较完整的个人项目特征：

- 使用 LangGraph 组织固定研究 DAG，并对补充检索设置了轮次和查询总量预算。
- 将本地知识库、个人知识库和实时 Web 证据统一到同一套证据合同与引用体系中。
- 个人知识库按用户使用独立 Qdrant collection，支持增量入库、同名覆盖和删除。
- 具备结构化模型输出桥接、引用 claims/evidence 校验、错误分类和降级路径。
- 包含 SQLite 状态机、僵尸回合回收、回合取消、会话串行执行和较完整的后端测试。
- 已有真实模型、Web 检索和个人知识库的端到端验证记录。

当前主要短板不在“功能数量不够”，而在以下几类工程闭环尚未完全形成：

1. 前端真实体验与后端能力没有完全对齐。
2. WebSocket 断线恢复缺少持久化状态对账。
3. 干净环境的首次运行路径仍有文档缺口。
4. 认证、限流和多实例部署边界仍是演示级实现。
5. API 文档、配置检查和真实质量指标还没有完全自动化闭环。

## 3. 详细待修复事项

### 3.1 前端实际渲染流式回答

**现象**

后端已经通过 `answer.delta` 发送正文增量，`useConversationApp` 也会将增量累积到 `streamingText`。但 `ConversationWorkspace` 的答案展示逻辑当前主要读取 `turn.answer` 或 `result.answer`，没有将运行中的 `streamingText` 作为展示内容。

因此代码层面已经存在“真流式”链路，用户界面却可能要等回合完成、详情刷新后才显示完整正文，实际体验与设计目标不一致。

**影响**

- 首字时间指标无法真实反映用户看到首字的时间。
- 长耗时研究回合在完成前缺少正文反馈。
- 简历中声称“支持流式回答”时，面试演示可能暴露前端没有实时渲染的问题。

**修复建议**

- 运行中的当前回合优先展示 `streamingText`。
- `streamingText` 为空时显示现有的“正在整理回答”占位文案。
- `turn.completed` 后以服务端持久化的正式 `answer` 为权威内容，清理临时流式状态。
- 明确增量文本和最终答案的覆盖关系，避免详情刷新与增量事件同时到达时发生重复拼接。
- 保持流式开关关闭时的原有 JSON 路径不变。

**验收标准**

- 收到首个 `answer.delta` 后页面立即出现正文。
- 流式过程中正文可以持续增长，不需要等待 `turn.completed`。
- 完成态不会重复显示增量文本。
- 流式路径失败并回退到 JSON 路径时，页面仍能得到唯一的最终答案。
- 增加组件测试，覆盖“增量展示 → 完成态覆盖 → 临时状态清理”。

**优先级与风险**

P1。改动集中在展示层和状态选择逻辑，风险较低，但必须防止与现有详情刷新产生竞态。

### 3.2 WebSocket 重连后的状态对账

**现象**

WebSocket 事件总线是进程内内存实现，没有事件 replay。前端在重连成功后目前只清除连接错误，没有主动重新读取当前会话或当前回合的持久化状态。

如果断线期间错过 `turn.completed` 或 `turn.failed`，前端可能一直保留 running 状态、stage 文案或 loading 状态。虽然回合结果已经写入数据库，但页面无法自动恢复到正确状态。

**影响**

- 网络抖动、浏览器切后台或服务重启后可能出现状态卡死。
- 用户可能重复提交问题，因为页面误以为上一回合仍未结束。
- 仅依赖 sequence gap 日志无法恢复已丢失的事件。

**修复建议**

- WebSocket 重连成功后立即刷新当前会话详情。
- 以服务端持久化 turn 状态作为最终事实源，恢复答案、结果、错误和运行状态。
- 如果服务端显示回合已经结束，则清理 stage、计划预览、`runningTurnId` 和 `streamingText`。
- 如果服务端仍处于 running，则保留运行状态并继续接收后续事件。
- 保留 sequence gap 日志，用于诊断事件丢失。
- 后续若需要更强可靠性，再设计基于 sequence 的事件回放或“当前状态快照”接口，不要仅依赖内存 EventBus。

**验收标准**

- 模拟断线并跳过完成事件后，重连能够恢复为 completed 或 failed。
- 断线期间回合仍在执行时，重连后页面仍显示正确的 running 状态。
- 重连刷新不会造成答案重复、重复追加或状态倒退。
- 增加 Hook 测试，覆盖断线、重连、错过终态事件和服务端状态覆盖前端临时状态。

**优先级与风险**

P1。属于可靠性缺陷，涉及事件状态与 HTTP 状态的竞态，需要明确谁是最终事实源。

### 3.3 修正 README 首次运行流程

**现象**

README 当前给出的 `python scripts/index_knowledge.py` 命令没有传入脚本要求的 `--manifest`、`--index-path` 和 `--collection` 三个必填参数，按文档直接执行会失败。

同时，`.data` 被 Git 忽略，干净 clone 默认没有本地知识库索引；`data/knowledge/beginner-v2/README.md` 中已经存在更完整的构建、校验和索引流程，但顶层 README 没有把这些步骤串起来。README 的模型介绍还存在默认值不一致：正文写的是 `openai:gpt-4.1-mini`，配置和代码默认值是 `deepseek-v4-flash`。

**影响**

- 面试官或其他开发者无法按 README 快速复现项目。
- 首次启动可能误以为项目不可用，降低项目完成度印象。
- 文档与代码配置不一致会导致错误的模型选择和排障方向。

**修复建议**

- 将 README 改成可复制执行的 clean-clone 流程：安装依赖、配置环境、准备语料、构建 manifest、校验索引、写入索引、启动服务和启动前端。
- 明确主语料来源、manifest 的位置、本地索引的位置，以及哪些产物不会提交到 Git。
- 使用带显式参数的索引命令，并说明 `--validate-only` 的用途。
- 统一 README、`.env.example`、`settings.py` 和实际测试记录中的模型默认值。
- 对缺少真实 API Key 的情况，说明可以运行的离线测试范围以及会被关闭的能力。
- 增加“已知限制”章节，明确当前默认面向单机个人部署。

**验收标准**

- 新用户从干净 clone 按 README 执行，不会遇到缺少必填参数的问题。
- 所有默认配置与代码和 `.env.example` 一致。
- 至少存在一条完整、可复制的知识库构建与索引命令。
- 文档不会要求提交密钥、数据库、本地模型缓存或 Qdrant 索引。
- 可通过简单文档检查或 CI grep 防止命令和默认值再次漂移。

**优先级与风险**

P1。主要是文档和复现流程修正，风险低，但对个人项目展示价值很高。

### 3.4 同步 OpenAPI 文档

**现象**

运行时已经存在 `DELETE /api/conversations/{conversation_id}/turns/{turn_id}` 回合取消接口，但静态文件 `docs/openapi.json` 对应路径只有 GET，缺少 DELETE 操作。

**影响**

- 前端和 API 使用者无法仅依赖 OpenAPI 文档发现取消能力。
- 静态 API 合同不再是运行时接口的可信快照。
- 面试中展示“有 OpenAPI 合同”时容易被发现文档漂移。

**修复建议**

- 从当前 FastAPI 应用重新导出 `docs/openapi.json`。
- 将 OpenAPI 导出或 schema 对比加入开发命令和 CI。
- 对新增的取消接口补充 204、404、409 等响应说明。
- 保持现有 API/WS 向后兼容，不通过重写 schema 改变既有字段语义。

**验收标准**

- 静态 OpenAPI 与运行时 `app.openapi()` 等价。
- 取消回合接口在文档中包含正确的路径参数、响应码和错误语义。
- 后续接口发生变化时，CI 能够发现 schema 漂移。

**优先级与风险**

P2。风险较低，适合在前三项完成后立即处理。

### 3.5 更新 doctor 配置清单

**现象**

`scripts/doctor.py` 的配置键清单落后于实际代码消费情况，可能错误提示以下配置未被消费：

- `MODEL_NAME_LIGHT`
- `MODEL_STREAMED_SYNTHESIS`
- `MAX_TURNS_PER_CONVERSATION`
- `HISTORY_TOKEN_BUDGET`
- `EMBEDDING_VERSION`
- `EMBEDDING_DIMENSION`
- 角色级 temperature 配置
- `CITATIONS_CHINESE_TOKENIZER`

**影响**

- 合法配置产生误报，降低 doctor 的可信度。
- 用户可能忽略真正的环境变量拼写错误。
- 配置清单不能作为项目配置治理的可靠入口。

**修复建议**

- 以 `settings.py` 和直接 `os.getenv` 调用为来源重新整理 consumed key 清单。
- 区分环境变量、内部常量和历史遗留变量，不要把仅存在于代码中的常量当成环境变量要求用户配置。
- 为 doctor 增加配置对账测试。
- 让测试覆盖合法配置无误报、拼写错误有告警、历史遗留键按约定提示、可选配置缺失不报错等情况。

**验收标准**

- 当前 `.env.example` 逐项执行 doctor 不出现错误误报。
- 新增配置能够通过测试提醒开发者同步 doctor。
- 输出清楚区分“可选缺失”“未消费”“历史遗留”和“疑似拼写错误”。

**优先级与风险**

P2。改动范围小，但应避免为了消除告警而错误扩大配置消费范围。

### 3.6 加固认证与滥用防护

**现象**

新数据库当前会自动创建 `admin/0000` 和 `user/0000`。认证链路缺少首次改密、用户创建、密码修改、登录失败限流、防暴力破解、用户级成本限制和并发限制等能力。

这对本机演示可以接受，但如果服务被暴露到公网，固定弱密码和无登录限流会构成明显风险。

**影响**

- 管理员账户可能被直接猜解。
- 模型调用和 Web 检索可能被恶意消耗，产生不可控成本。
- 高并发请求可能拖垮单进程事件循环或模型 provider。
- 当前工程不能安全地宣称支持公网部署。

**修复建议**

- 生产模式禁止继续使用固定默认密码。
- 首次启动通过环境变量或一次性初始化流程设置管理员密码。
- 增加密码修改能力和基本密码策略。
- 对登录接口增加基于 IP 和用户名的失败限流、短期锁定或退避。
- 增加用户级并发数、每日调用次数、回合数、token 或成本限制。
- 明确 Cookie、CORS、CSRF 和 HTTPS 要求；公网环境默认启用安全 Cookie。
- 在 README 中明确本地部署与公网部署的安全差异。

**验收标准**

- 生产配置不允许使用固定弱密码进入管理员账户。
- 连续登录失败会触发限流或锁定。
- 普通用户无法访问管理员接口和其他用户的个人知识库。
- 用户级并发和资源限制有对应测试。
- 错误响应不会泄露模型、数据库、密钥或内部路径信息。

**优先级与风险**

本地个人部署为 P2；任何公网部署为 P1。认证改动邻近安全语义，实施前应先写失败的敌意测试，再修改实现。

### 3.7 明确单进程限制，或引入共享运行时

**现象**

回合执行 task 注册表、会话锁和 WebSocket EventBus 均为进程内状态，回合通过 `asyncio.create_task` 在当前进程中执行。直接启用多 worker 或多实例部署后，不同请求可能落到不同进程。

**潜在问题**

- 创建回合的进程不一定是执行或取消回合的进程。
- 进程内锁无法阻止不同 worker 同时执行同一会话的回合。
- EventBus 事件不会自动广播到其他进程。
- WebSocket 连接到不同 worker 时可能收不到回合事件。
- 服务重启会丢失内存中的任务映射和事件历史。

**修复建议**

短期应明确支持边界：

- 默认只支持单进程、单实例个人部署。
- 启动示例不要默认给出多 worker 配置。
- README 说明服务重启、僵尸回合回收和事件丢失行为。

如果未来确实需要多实例，再单独设计分布式运行时：

- 使用持久化任务队列承载回合执行。
- 使用 Redis 或数据库实现跨进程锁和任务租约。
- 使用 Redis Streams、消息队列或持久化事件表承载事件。
- 设计任务幂等、取消、重试、超时和事件回放语义。

**验收标准**

- 文档明确列出支持和不支持的部署方式。
- 启动配置不会诱导用户使用多 worker。
- 若实现多实例支持，必须补充跨进程创建、执行、取消、事件投递和重连测试。

**优先级与风险**

个人简历项目为 P2；准备公网多实例部署时为 P1。不要为了“看起来支持生产”而仅修改启动参数，必须先解决共享状态问题。

### 3.8 拆分 liveness/readiness

**现象**

当前 `/health` 即使模型或知识库不可用，也返回 `status=ok`。这只能说明 Web 进程能够响应请求，不能说明系统已经具备完整研究能力。

**影响**

- 部署平台可能误判服务完全就绪。
- 用户无法区分服务进程故障和某一类证据源暂不可用。
- 诊断信息不足，降级状态不够明确。

**修复建议**

- 保留简单的 `/live` 或现有 `/health` 作为 liveness 检查。
- 增加 `/ready`，根据模型配置、知识库索引和 Web provider 状态返回 `ready`、`degraded` 或 `not_ready`。
- Tavily 未配置时不应阻塞纯本地研究能力，但应在 readiness 中明确 Web 能力不可用。
- 健康检查不执行真实 LLM 调用，避免检查本身产生费用和延迟。
- 健康响应不得暴露密钥、绝对路径或内部异常栈。

**验收标准**

- 进程存活但知识库缺失时，liveness 通过、readiness 反映不可用。
- Tavily 未配置时，服务可以以本地研究能力 degraded 状态运行。
- 模型配置缺失时，readiness 明确返回不可用原因类别，而不是笼统的 `ok`。

**优先级与风险**

P2。适合在部署边界明确后处理。

### 3.9 建立真实 LLM 评测

**现象**

当前离线 `dev-40` 评测使用 deterministic mock，已验证成功率和部分召回指标，但不能证明真实模型的回答质量、延迟或成本。现有评测中的 latency 可能为 `n/a`，cost 为 mock 的 `0.0`，citation real semantic evaluation 也不应被 mock 结果替代。

**影响**

- 无法客观比较提示词、模型路由、流式开关和检索策略的收益。
- `topic_recall_mean=0.6083` 容易被误解为回答准确率。
- 简历中的“准确率”“低延迟”“低成本”缺乏真实证据。

**修复建议**

- 建立 30～100 个固定 golden cases，覆盖单跳事实、多跳研究、时效问题、个人知识库、跨库冲突、证据不足、中文混合语料、追问承接、Web 关闭和 provider 不可用。
- 分别记录 retrieval Recall@K、source coverage、citation precision/recall、groundedness、unsupported-claim rate 和任务成功率。
- 记录 p50/p95 首字延迟、总延迟、输入输出 token 和估算成本。
- 区分 mock 离线评测、真实 provider 评测和人工抽检。
- 固化数据集版本、模型版本、关键配置和测试日期。
- 把失败案例和已知边界一并记录，而不是只展示成功率。

**验收标准**

- 至少有一组真实模型结果和一组可重复离线结果。
- 评测报告明确数据集、模型、配置、执行模式和指标定义。
- 不把 topic recall 直接包装成回答准确率。
- 能够对检索策略、模型路由和提示词修改前后进行可比实验。

**优先级与风险**

P2。不是上线阻塞项，但对简历项目的说服力提升最大。真实评测必须脱敏，不提交 API Key、Cookie 和个人文档内容。

### 3.10 增加前端 E2E 和展示材料

**现象**

后端单元测试和前端单元测试覆盖较完整，但前端真实 WebSocket 流程、断线重连、取消回合、知识库上传和多轮交互仍缺少端到端证明。仅展示代码和测试数量，面试官不容易快速理解产品体验。

**修复建议**

- 增加最小前端 E2E 流程：登录、创建会话、提交问题、观察进度、查看流式回答和引用。
- 增加取消运行中回合的 E2E 场景。
- 增加上传、检索和删除个人文档的 E2E 场景。
- 增加断线重连后恢复状态的 E2E 场景。
- 增加架构图，展示 planner、retriever、reviewer、supplemental loop、synthesizer 和三类证据源。
- 增加一段 1～2 分钟的脱敏演示视频或几张关键截图。
- README 增加“设计取舍”和“已知限制”，主动说明单进程、模型依赖、成本和评测边界。

**验收标准**

- 本地或 CI 可以执行至少一条核心前端 E2E 流程。
- README 能在几分钟内说明项目解决的问题、核心架构、技术取舍和限制。
- 演示材料不包含真实密钥、Cookie、个人文档内容或内部绝对路径。

**优先级与风险**

P2。主要提升验证性和展示质量，不应以牺牲核心功能稳定性为代价追求视觉包装。

## 4. 分阶段执行建议

### 阶段一：演示和复现闭环

先完成 1～3 项：前端流式展示、WebSocket 重连对账和 README 修正。这一阶段完成后，项目的核心能力才能在演示和干净环境中被正确观察到。

### 阶段二：工程合同闭环

完成 4～5 项：OpenAPI 同步和 doctor 配置对账。建议同时加入自动检查，避免之后每次改接口或配置都重新人工排查。

### 阶段三：部署边界和安全闭环

如果项目只作为本地简历项目，可以先完成单进程限制说明，再视时间处理认证细节。如果准备公网展示，应优先完成认证、限流、资源配额和 readiness，再考虑多实例化。

### 阶段四：质量证据和展示闭环

完成真实 LLM 评测，再补前端 E2E、架构图和演示视频。评测结果应成为简历中量化项目价值的主要依据。

## 5. 统一验收与实施约束

- 不削弱 fail-closed、安全隔离、错误脱敏、引用校验和 API/WS 向后兼容约束。
- 涉及认证、数据隔离、任务取消或错误语义的改动，先写注定失败的敌意测试，再实现修复。
- 每项修复至少补充一个能够证明问题已解决的测试或可重复验证命令。
- 完整回归应保持后端测试全绿、ruff 全绿；前端依赖完整时执行 lint、build、Vitest 和核心 E2E。
- 不提交 `.env`、真实密钥、Cookie、数据库、本地模型缓存和 Qdrant 索引。
- 所有评测指标必须标注测试模式，禁止将 mock 数据包装成真实生产指标。
- 每个任务独立提交，commit message 以任务编号或明确事项开头，测试通过后再提交。

## 6. 简历表述建议

在完成第一阶段前，建议表述为：

> 面向个人部署的多轮研究助手原型，基于 LangGraph 编排有界补充检索流程，融合本地知识库、个人文档知识库与实时 Web 证据，输出带可追溯引用的回答，并具备会话状态持久化、用户数据隔离和故障降级能力。

在完成真实评测和前端 E2E 后，可以进一步补充经过验证的指标，例如：

- 评测集规模和覆盖范围；
- 检索 Recall@K 或 source coverage；
- 首字和总延迟的 p50/p95；
- 单回合 token/cost；
- 断线恢复、引用校验或个人知识库隔离的测试结果。

不要在缺少真实实验数据时使用“生产级”“高并发”“准确率达到 X%”等表述。
